## What

Add three machine-readable fields to every fixture's `expectations.md` (5 existing + 2 planned from T2.3). Add these as a YAML frontmatter block at the top of each `expectations.md`:

```yaml
---
dispatch_skill: <skill-name>
ignore_fields: [updated_at, timestamp, actual_publish_time]
max_attempts: 3
---
```

Values per fixture:

| Fixture | `dispatch_skill` | Notes |
|---------|-----------------|-------|
| `quick-social-happy` | `signal-publish` | Already at publish phase; publish completes to done |
| `review-rejection-rework` | `signal-review` | Redispatch after user reject reply |
| `campaign-blocked-at-intake` | `signal-brief` | Re-evaluation of campaign-scope brief |
| `publish-duplicate-skipped` | `signal-publish` | Re-publish detects duplicate |
| `compliance-default-clear` | `signal-review` | Review with compliance at clear |
| `review-redirect-create` | `signal` | Orchestrator routing test (T2.3) |
| `publish-done-archive` | `signal` | Orchestrator terminal transition test (T2.3) |

Do NOT add the fields to the 2 orchestrator fixtures (T2.3) — those don't exist yet. T2.3 adds them as part of creating the fixture from scratch.

## Why

AC 2, AC 4, AC 5 — the replay harness needs `dispatch_skill:` to know which skill to invoke, `ignore_fields:` to skip non-deterministic timestamp fields during mutation diffs, and `max_attempts:` to configure the retry policy. Without these, the harness must hardcode mappings or guess.

## Done when

- All 5 existing `expectations.md` files have the YAML frontmatter with correct `dispatch_skill:` values.
- `run-signal-fixtures.sh` still exits 0 after the additions (new frontmatter doesn't break existing checks).
- Each `dispatch_skill:` value matches an existing skill folder under `skills/`.
